## 2. Ход работы

1. **Подготовка.** Создан репозиторий, `main` защищена (PR + 1 одобрение + зелёный CI), от неё создана `dev`.
2. **Контракт.** Вся команда согласовала `API_CONTRACT.md` v1.0: схема `Task`, `POST /api/tasks`,
   `POST /api/webhooks/task_created`, тело вебхука — объект `Task` без обёртки.
   Уточнение заголовков и политики повторов было оставлено разработчикам сервисов.
3. **Параллельная разработка** в ветках `feature/tasks-service` и `feature/notifications-service`,
   созданных от `dev`. Каждый разработчик дописал в раздел 4.2 контракта свою часть.
4. **Интеграция.**
   - PR #1 `feature/tasks-service` → `dev` (открыл Ив Вик): Tech Lead запросил изменения
     (пример curl в README сервиса), Рог Вад внёс исправление, PR одобрен и смержен.
   - `feature/notifications-service`: `git pull --rebase origin dev` → **конфликт** в `API_CONTRACT.md`.
   - Конфликт разрешён вручную (раздел 3), `git rebase --continue`, `git push --force-with-lease`.
   - PR #2 → `dev` (открыл Tech Lead за Кул Ника): ревью Ив Вик, смержен.
   - PR #3 (интеграционные тесты и отчёт) → `dev`: ревью Ив Вик, смержен.
   - Запуск обоих сервисов, ручная e2e-проверка через curl (раздел 5).
   - PR `dev` → `main`: ревью Ив Вик, CI зелёный, смержен.

## 3. Конфликт при слиянии

**Где:** `API_CONTRACT.md`, два участка: раздел 4.2 «Формат сообщения вебхука» и таблица «История изменений».

**Причина:** обе ветки заменили одну и ту же строку-заглушку контракта v1.0
(«Дополнительные заголовки и правила повторной доставки: будут согласованы при разработке»)
своим текстом и обе добавили в историю строку с номером версии `1.1`.

Фрагмент, который Git показал при rebase:

```diff
++<<<<<<< HEAD
 +| Заголовок            | Назначение                                              |
 +| `X-Event-Type`       | Тип события, всегда `task.created`                      |
 +| `X-Event-Id`         | UUID события, **одинаковый во всех повторных попытках** |
 +| `X-Delivery-Attempt` | Номер попытки доставки, начиная с 1                     |
 +
 +Повторная доставка (реализует Task Service): ...
++=======
+ Идемпотентность (реализует Notification Service):
+ - ключ события — заголовок `X-Event-Id`; если заголовок не передан, используется `id` задачи; ...
+ ### 4.3. `GET /api/notifications` — последние уведомления ...
++>>>>>>> (docs(contract): v1.1 — идемпотентность вебхука, ответ 503, GET /api/notifications)
   ...
   | 1.0    | Первая версия контракта (вся команда) |
++<<<<<<< HEAD
 +| 1.1    | Заголовки события и политика повторной доставки (Task Service) |
++=======
+ | 1.1    | Идемпотентность вебхука, ответ 503, `GET /api/notifications` (Notification Service) |
++>>>>>>> ...
```

**Разбор.** Изменения не противоречат, а дополняют друг друга: Task Service описал, *что он отправляет*
(заголовки и повторы), Notification Service — *как он обрабатывает повторы* (идемпотентность).
Но Notification Service опирается на заголовок `X-Event-Id`, который появился только в ветке Task Service, —
без объединения контракт был бы неполным. Кроме того, одна версия `1.1` не может описывать два разных изменения.

## 4. Принятые решения

| # | Решение | Обоснование |
|---|---------|-------------|
| 1 | В разделе 4.2 оставлены **обе** части: сначала заголовки и политика повторов, затем идемпотентность | Порядок соответствует потоку данных: отправитель → получатель |
| 2 | Изменения Notification Service получили версию **1.2**, итоговая версия контракта — 1.2 | Первым был смержен PR Task Service, его версия 1.1 уже в `dev`; номера версий не должны повторяться |
| 3 | Зафиксировано: `X-Event-Id` одинаков во всех попытках и является ключом дедупликации | Связывает политику повторов с идемпотентностью; без этого повтор дал бы двойное уведомление |
| 4 | Ответ 503 от Notification Service попадает под правило «повтор при 5xx» | Проверено: Task Service повторяет любые 5xx, изменения кода не потребовались |
| 5 | Использован `git pull --rebase` вместо merge-коммита | Линейная история ветки, конфликт разрешается в конкретном коммите контракта |
| 6 | Схема `Task` продублирована в каждом сервисе, а не вынесена в общий пакет | Сервисы деплоятся независимо; совместимость гарантирует контракт и интеграционный тест |

Код сервисов конфликтов не вызвал: команды работали в разных каталогах (`task_service/`, `notification_service/`).

## 5. Интеграционное тестирование

### Автоматические тесты

```text
python -m pytest
task_service          17 passed   (CRUD, валидация, формат вебхука, повторы, отказ получателя)
notification_service   9 passed   (приём, лог, дубли, 422, недоступный лог → 503)
tests/integration      2 passed   (оба сервиса в отдельных процессах uvicorn)
```

### Ручная сквозная проверка (curl)

Сервисы запущены `scripts/start_services.ps1`, проверка — `scripts/e2e_check.ps1`.

```text
== 1. Создаём задачу (ожидаем 201)
HTTP/1.1 201 Created
{"title":"Сдать лабораторную","description":"МДК 02.02, ЛР 2","status":"new",
 "id":"c475173c-995e-462a-a162-775901e578b9","created_at":"2026-09-16T12:47:54.226933Z"}

== 2. Задача сохранена в Task Service
[{"title":"Сдать лабораторную", ..., "id":"c475173c-995e-462a-a162-775901e578b9", ...}]

== 3. Счётчики доставки вебхука
{"status":"ok","webhook_delivered":1,"webhook_failed":0}

== 4. Notification Service получил событие
[{"event_id":"def13475-2bab-474d-994f-2d2e3553a581","received_at":"2026-09-16T12:47:54.247239Z",
  "message":"Создана задача «Сдать лабораторную» (статус: new)",
  "task":{"id":"c475173c-995e-462a-a162-775901e578b9", ...}}]
```

Результат: задача сохранена, вебхук доставлен с первой попытки (~20 мс), уведомление записано
в `logs/notifications.log`.

### Проверка отказа

Notification Service остановлен, отправлен `POST /api/tasks`:

```text

WARNING task_service.notifier: Вебхук 3e2ecadf-... не доставлен (timeout), попытка 1/5, повтор через 0.5 c
WARNING task_service.notifier: Вебхук 3e2ecadf-... не доставлен (timeout), попытка 2/5, повтор через 1.0 c
WARNING task_service.notifier: Вебхук 3e2ecadf-... не доставлен (timeout), попытка 3/5, повтор через 2.0 c
WARNING task_service.notifier: Вебхук 3e2ecadf-... не доставлен (timeout), попытка 4/5, повтор через 4.0 c
```

Task Service не упал и продолжил обслуживать запросы. Сценарий «получатель поднялся позже» покрыт
интеграционным тестом `test_notification_delivered_after_service_comes_back`.

## 6. Выводы

- Contract-first позволил разрабатывать сервисы параллельно: код интегрировался без правок.
- Единственный конфликт возник в общем файле контракта, куда обе команды дописывали «свои» разделы.
  В следующий раз стоит заранее разделить контракт на подразделы-заготовки с владельцами
  или вносить изменения контракта отдельным маленьким PR до начала разработки.
- Ограничения прототипа (хранение в памяти, потеря событий при перезапуске) описаны в README сервисов;
  для продакшена нужны БД и брокер сообщений.
